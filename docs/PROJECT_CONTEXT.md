# PROJECT_CONTEXT

## 1. プロジェクト概要

本プロジェクトでは、「ぶいすぽっ！」所属メンバーの配信アーカイブ情報を集約し、複数メンバーを横断して過去配信を探索できるWebシステムを開発する。

主な探索軸は次のとおり。

- メンバー
- ゲーム / topic
- 配信日時・期間
- キーワード

例:

- VALORANTを配信していたメンバーとその過去配信を一覧表示する
- 特定メンバーが過去にMinecraftを配信した動画を探す
- 特定期間の特定ゲーム配信を横断的に探す

## 2. 開発背景

YouTubeでは基本的にチャンネル単位で動画・配信アーカイブを確認することになるため、所属メンバーを横断した探索がしにくい。

所属メンバーが増えたことで、次のような不便を感じている。

- 誰が最近どのゲームを配信しているのか把握しきれない
- 特定ゲームを遊んでいるメンバーを横断的に探しづらい
- 過去に見た・見かけた配信を後から探しづらい
- 「メンバー × ゲーム × 期間」のような条件で探しづらい

本システムはYouTubeを置き換えるものではなく、**YouTube上に分散している配信を、自分が使いたい条件で再探索しやすくする補助システム**として位置付ける。

## 3. 想定ユーザー

### Primary User

開発者本人。

自分自身が実際に継続利用することを最重要とする。

### Future User

利用規約・データ利用条件等に問題がなければ、将来的には同様の課題を持つ他の利用者もアクセスできる形で外部公開することを目指す。

ただし、外部公開は確定要件ではなく、データソースの利用条件等を確認したうえで最終判断する。

## 5. 開発原則

### 5.1 小さく動かしてから広げる

基本サイクルは次のとおり。

1. 最小構成で実装する
2. 実際に動かす
3. 問題・制約を確認する
4. 解決策を検討する
5. 必要な技術を導入する

### 5.2 技術導入を目的化しない

Redis、AWS、Queue、Microservices等を「高度そうだから」という理由だけで導入しない。

例:

- データ取得が遅い → バッチ・非同期処理を検討
- 検索が遅い → DB Indexや検索機能を検討
- APIアクセスが重複する → Cacheを検討
- ローカルだけでは扱いづらい → PostgreSQL等を検討
- デプロイしづらい → Dockerを検討
- 手動デプロイが面倒 → CI/CDを検討
- 公開環境の状態が分からない → Logging / Monitoringを検討

### 5.3 Monolith First

個人開発であり、MVP段階では単純なMonolith構成を基本とする。

Microservices等への分割は、明確な必要性が発生した場合のみ検討する。

### 5.4 テスト可能な設計

UI、外部APIアクセス、ビジネスロジック、DBアクセス等を必要に応じて分離し、pytest等でテストしやすい構造を目指す。

### 5.5 Git / GitHubを積極的に利用する

- 適切なコミット単位
- feature / fix単位のbranch
- README整備
- Issue管理
- GitHub Actions
- Secret管理
- 公開してはいけない情報の分離

を実践する。

## 6. 費用方針

原則として、開発・MVP・初期公開までは無料で進める。

有料サービスを導入する場合は、必ず次を確認する。

1. 無料構成では何が問題なのか
2. いくらかかるのか
3. 支払うことで何が改善するのか
4. 他に無料または低コストの選択肢がないか

独自ドメイン、常時稼働サーバー、有料DB等は現時点では必須ではない。

## 7. 外部公開方針

開発初期はローカルで自分だけが使用する。

完成度が上がり、データソース・API・名称・画像等の利用条件に問題がなければ、最終的には誰でもURLからアクセスできるWebアプリとして公開することを目標とする。

公開可否は、データソースPoCおよび公開前の規約確認を踏まえて判断する。

## 8. 現在の重要課題

最優先で確認すべきなのは、**配信ごとの具体的なゲーム名をどのように得るか**である。

動画ID、タイトル、日時等を取得できても、VALORANT、Minecraft、Apex Legends等のゲーム情報を安定して取得・利用できなければ、本システムの主要価値であるゲーム横断探索が成立しない。

そのため、Webアプリ本体の実装前にデータソースPoCを行う。

## 9. 現在のフェーズ

Phase 0: Data Source Feasibility Study / PoC

次フェーズへ進む条件:

- 採用するデータソースを決められる
- MVPで必要なデータを取得可能と確認できる
- game / topic情報の扱いを決められる
- API制限・利用条件を把握できる
- MVPで保存するデータ項目を決められる
